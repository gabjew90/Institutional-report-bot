## Graded items

### 1. Adjudication Rule 6 field-name bug — P0, and worse than the handoff frames it

[observed] `ADJUDICATION_SYSTEM`'s schema emits `by_when`; Rule 6's filter reads `pred['deadline']`. The key never exists, `_deadline_ok()` returns False for every prediction, and 10 of 10 predictions were dropped this run (9 on `ai capex financing`, 1 on `ai cloud monetization`). All 5 themes validated with empty prediction arrays.

The handoff calls this "silent, permanent, 100% data-loss." That undersells it in two ways.

**First: it is not merely data loss, it is a subsystem that has never once functioned.** [inferred] If the filter has always read the wrong key, then no adjudicated packet in the pipeline's history has ever delivered a falsifiable prediction to DRAFT. Every invalidation the pulse has ever published — including all four in today's final — was written by DRAFT from its own reading of the per-PDF inputs, not from a structured, lint-validated, deadline-bearing prediction. The entire apparatus of "adjudication produces falsifiable predictions and lints them" is scaffolding around an empty room.

**Second: the failure is invisible precisely because DRAFT compensates.** [observed] Today's four closes are decent — "above 100 basis points" (attributed to Morgan Stanley), "if the 30-year breaks above Monday's 5.23% close," JPMorgan's December hike as a kill condition. Nobody looking at the output would suspect the packets were empty. [inferred] That is the mechanism by which this survived: the only signal was an adjudication summary reading "5 validated, 0 discarded," which is exactly what a healthy run looks like. The observable quality cost is real but subtle — theme 3's close has no level and no date, and it is the theme whose adjudicated packet had no surviving prediction to hand DRAFT.

**The deeper bug is that "0 discarded" was reported as success.** [observed] A packet that entered Rule 6 with 9 predictions and left with 0 was marked validated. That is the check that should have caught this on run 1 and did not exist. Fixing the key name without also fixing the validator leaves the same class of failure available to the next schema drift.

**Verdict: correctly identified as the highest-value fix available, and the handoff is right that it should be fixed first.** The fix is two lines plus an assertion, and the assertion matters more than the two lines. See Suggested changes.

**But the reasoning in the handoff is partly circular and should not be recorded as-is.** [inferred] "The shipped document is the stronger and the more validated of the two" is true, but the causation runs the other way: it is more validated *because the validators ran on it*. EDIT's second pass was a normal prose-tightening pass (8 words shorter, no new facts, no new errors) that simply had not been through any gate. The correct summary is: *the intermediate was the right artifact to ship because it was the one the gates had processed, and EDIT's final added nothing that would have justified re-running them.* Recording it as "EDIT's second pass was worse" would set up the wrong instinct next time.

**The process failure is severe and the outcome was luck.** [observed] The race was detected because the FIXUP agent noticed its own prompt disagreed with disk and said so. That is not a control — it is an agent being conscientious. [inferred] Invert the run: EDIT's first write contains a factual error, its second write fixes it, the watcher fires on the first, and the pipeline ships the broken version with a clean gate record and no anomaly for anyone to report. Nothing in the current pipeline would notice.

[observed] A second consequence already visible in this run: the recorded EDIT metric (11,081 → 11,119 chars, +0.34%) is measuring the intermediate, so the stage's own telemetry is wrong for this run and would be wrong on every run the race fires.

**Verdict: right ship decision, unacceptable detection path.** Two fixes, both cheap: stop treating first-write as completion (use the agent's returned completion message or a sentinel), and add a hash comparison at every stage boundary between the on-disk document and the document the next stage's prompt embeds. The second one is deterministic, ~15 lines, and would have converted this from "an agent happened to mention it" into a hard failure at the EDIT→LINT boundary.

### 3. Applying all four adversarial SOFT findings after the gate returned CONTINUE

**The right call, and the routine is what should change — not the operator's behavior.**

[observed] All four findings were checkable factual defects verified by a fresh-context checker holding the full 29-PDF corpus in a 222KB prompt. [observed] All four fixes landed, and the orchestrator then re-ran lint (0 hard), `final_validate --recheck` (0 hard), strip (clean) and preflight (PASS) — so the deviation was made *safe*, not merely made. [observed] The corrections were net-additive: the $2.7tn/$3.1tn fix added a figure rather than deleting a claim.

The routine's literal instruction — soft findings "change nothing here" — would have shipped a document that told readers CrowdStrike matched a consensus the pulse's own prior edition published as $0.30, and that asserted Nvidia is rated above GOOGL and AMZN when the cited bank calls all three similarly rated. A routine whose plain reading produces that outcome, on a run where the operator had to override it to get the right answer, is a routine that needs editing. Filing this as a "declared deviation" preserves the wrong default.

**On promoting these classes to hard — split the answer by class, because promoting all four would be wrong.**

- **`figure-mismatch` against the pulse's own published ledger (the CrowdStrike case): promote to hard, and do it in code, not in the checker.** [inferred] This is definitionally the same defect as `consensus-amnesia`, which is already a hard validator. The only reason it arrived as a soft adversarial finding is that `consensus-amnesia` tests for *absence or denial* of a ledger name's consensus, not for a *wrong verdict against a present one*. The ledger holds $0.30, the final holds $0.31 and the word "matched"; the comparison is arithmetic. Per CLAUDE.md's deterministic-first rule, this belongs in `final_validate` as an extension of the existing check, and the corresponding adversarial-prompt text should be deleted in the same commit.
