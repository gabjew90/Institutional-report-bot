## Notable pattern 1: the "Abe's holdings" thread (00:17-00:18 UTC) hit a figure-provenance bug that is already fixed in this checkout

Three turns in 26 seconds, two askers, one underlying tool
(`lookup_trade_log caller=abe kind=open`, `status=ok`, ~450 chars,
unchanged across all three calls):

- **00:17:37 dovahjo** asked for Abe's holdings. The raw model output
  (visible in the `<details>` block) correctly rendered all 8 tool-
  sourced positions ("TSLA 350(P) 09-09 @3.53", …). The **delivered**
  answer was two words: "Current book:" — every position line was
  stripped. Guard: `figure-provenance:stripped:1`.
- **00:17:58 spockbones**, replying to that truncated message with
  "Nice book," got the full 8-line list back, verbatim-matching the
  raw model output from the first turn, no guard firing this time.
- **00:18:03 dovahjo**, replying "You didn't show anything," got the
  full list again — but this time with an unearned
  `⚠️ Couldn't verify these specifics against a live source — treat
  the exact numbers as unconfirmed.` tacked on, despite the numbers
  being the same tool-sourced ones from `lookup_trade_log status=ok`.
  Guard: `figure-provenance:all-unsourced`.

`discord_bot/figure_provenance.py` narrates this incident in its own
source comment, verbatim down to the asker's reply:

> "(2026-09-08: 'what are Abe's current holdings' shipped as the two
> words 'Current book:' with all eight positions stripped, and the
> asker replied 'You didn't show anything')."

The named root cause: the guard's evidence-side number extraction
(`_NUM_RE`) "deliberately refuses a number with a letter stuck to it,"
so a strike written the way the trade-log tool writes it (glued,
e.g. `350P`) was invisible as evidence even though the exact same
number appeared in the answer. The fix (`_OPT_STRIKE_RE`, a dedicated
pattern for glued option-contract notation feeding `evidence_values()`)
is present in this checkout, timestamped `2026-09-09T08:02:38-07:00`
— **after every turn in today's log** (first Abe's-holdings turn
00:17:37 UTC on 09-08, ~15 hours before the fix commit). This checkout
has only one commit, so git-blame can't date the fix more finely than
"the current deploy," but the timestamp alone post-dates the whole
log — this is a **predates-class** case, already fixed going forward.

I could not fully reproduce the fix's before/after behavior for this
exact pair of turns: `figure_provenance.check()` needs the full
model-facing evidence (the tool's raw JSON response), which is not
rendered in this log's `<details>` blocks — those show only the
*initial* prompt (system context + chat + question), sent **before**
the tool call. Running today's (fixed) `fp.check()` against the
visible prompt text alone still strips the same 8 lines, because the
tool's actual JSON payload — the real evidence — isn't in what I can
see. So I can confirm the bug is documented-and-addressed, and that
the fix's target (glued strike notation on the evidence side) matches
this incident's shape, but I can't independently re-run the exact
before/after on the hidden tool payload. No further action needed
from this queue; not added as a fresh finding since it's the same
already-fixed root cause the module's own comment names.

A fourth, later turn is consistent with (but doesn't prove) the fix
already being live same-day: **18:38:41 dovahjo** re-asked "show me
Abe's current open positions," got a fresh `lookup_trade_log` result
with the same `(P)`/`(C)` notation, and no guard fired at all — graded
CLEAN below.
