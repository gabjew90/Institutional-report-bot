- Actual headline CPI m/m: **+0.4%** (matched consensus) — answer says +0.07% (a "big miss")
- Actual headline CPI y/y: **+3.4%** — answer says +3.52%

- Actual core CPI y/y: **+2.4%** — answer says +2.67%

This is independently corroborated inside the same day's log: the
14:07:11 turn (BK, "what did CPI come in at?") answered the identical
question 96 minutes later via `WEB/FACT` grounding with real citations
(morningstar.com, wtvbam.com) and got every figure right — headline
+0.4% m/m / +3.4% y/y, core +0.3% m/m / +2.4% y/y, matching the BLS
release exactly. The two turns describe the same print and cannot both
be correct; the earlier one is the wrong one.

Note this is NOT a "no source" case under ground rule 5 — the tool
table shows `lookup_economic_calendar` returned `ok` with real content
(2558 chars) on the second call. The fabrication happened on top of a
successful-status tool call, which is the harder-to-catch shape: the
turn looks sourced (guardrails would normally say don't penalize a
tool-backed answer) but the specific numbers are wrong regardless.
Worth flagging: 12:31:27 UTC is 8:31:27 AM ET — about 90 seconds after
the standard 8:30 AM ET CPI release time. The likely mechanism is a
data-freshness gap: the calendar tool's underlying source had not yet
ingested the real print at that instant and returned stale/incomplete
data (possibly still showing forecast rows), and the model filled in
"actual" values with false precision instead of declining or hedging
on the release being seconds old. `status_handling` and
`decline_when_uncertain` are marked CONCERN rather than FAIL because
the tool's status genuinely was `ok` — the defect is in what the "ok"
payload contained (or in how confidently the model treated a
just-landed print), not in status-field handling per se.

Downstream propagation, not itself a new finding: the 12:35:38 turn

## Notable pattern

Same-question, different-answer within one day is a validation shape
this suite doesn't check anywhere: no class compares two turns against
each other, only single answers against their own tool/grounding
context. The 12:31:27 vs 14:07:11 CPI conflict was only catchable here
because a human (well, judge) read both turns in the same log and
noticed the numbers didn't match — worth having in mind if a
cross-turn consistency check is ever considered, though this is one
data point, not a pattern yet.
