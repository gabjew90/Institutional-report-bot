### #36, #37 — 23:20:51 & 23:21:33 UTC, vincenzo9231, "roast monsoon and don't hold back" / "dummy, I said roast @Monsoon" — FAIL (depth_match, decline_when_uncertain)

that bypasses Gemini entirely and therefore bypasses the whole
DRAFT/AUDIT/validator ladder).

vincenzo9231 asked the bot to roast Monsoon, twice (once directly,
once repeating himself after being called "dummy"). Both times the
delivered answer was:
> → **BK** sent **84** messages in #💬-stonks-yapping-💬 in the last 6
> hours (702 total, ~6.0h span).

and

> → **BK** sent **86** messages in #💬-stonks-yapping-💬 in the last 6
> hours (703 total, ~6.0h span).

Neither answer has anything to do with the question asked. This isn't
a fabrication in the traditional sense — the message counts are real,
tool-grounded numbers (`query_data`, `status=ok`) — but they answer a
question nobody asked. fabrication graded CONCERN rather than FAIL
because the specific numbers aren't false, just irrelevant; the real
failure is depth_match (the response shape is not "two tiers off,"
it's a different question's answer entirely) and decline_when_uncertain
(the system delivered a confident, specific, formatted statistic in
response to input its own classifier had no business being confident
about).

**Root cause, found by reading the code, not guessing:**
`discord_bot/bot.py:3009` — `_is_message_count_question()` — strips a
reply-chain prefix before scoring the question text, but only handles
two marker shapes: `"'s message to you]"` and `"'s message]"`
(`bot.py:3016-3019`). Both of vincenzo9231's turns instead use the
`[VERBATIM RECENT MESSAGES — ... — for accurate quoting when the
question references them; quote LINE FOR LINE]` block format (built
for a different feature — letting the bot quote a target user's
messages verbatim). That block is never stripped, so
`_MSG_COUNT_INTENT_RE` (`bot.py:2979-2984`, matching `how many /
number of / count of` within 40 chars of `messages/posts/texts`) scans
the *entire* unstripped blob — including one of the quoted historical
lines, which is itself `"@omniwiz (Wizard of Omni) how many total
messages have been sent in this channel"` (BK's real question from
22:18:13, interaction #24, quoted verbatim as chat-history context).
That line trips the regex, `_extract_message_count_target()`
(`bot.py:3022+`) then pattern-matches `@(\w[\w._-]*)` against the same
blob and finds `"@BK (bankerkyle)"` a few lines earlier (`"you got a
new disciple"`), and the short-circuit answers "how many messages has
BK sent" — a question composed entirely from misread history, with
zero relationship to "roast monsoon."

**Triage:** `scripts/validate_answer.py` returns `{"violations": []}`
against the delivered text (expected — the text is internally
coherent and its number is genuinely tool-grounded; there's nothing
wrong with the answer *as an answer to the question it thinks it's
answering*). This checkout has a single commit
(`git log --oneline | wc -l` → 1), so a deploy-timestamp check against
the turn time isn't possible here; `_is_message_count_question` is
live in the current deployed code and reproduces the exact failure,
so this reads as a live, current gap rather than something already
fixed after these turns. **Bucket: regex-able**, though the fix
belongs in the router-intent layer (`bot.py`), not
`ask_response_validate.py` — the CLI validator has no way to know the
"right" answer's topic, only whether the delivered answer's own claims
are grounded.

Candidate fixture (for whatever harness exercises
`_is_message_count_question` / `_extract_message_count_target`
directly, since `scripts/ask_fixture_run.py`'s `tool_stubs` approach
targets the Gemini path, not this short-circuit):
```
question: (
    "[VERBATIM RECENT MESSAGES — Monsoon (reportufirst) — for accurate\n"
    "quoting when the question references them; quote LINE FOR LINE]\n"
    "  2026-09-09T22:18 #x — @omniwiz how many total messages have been sent in this channel\n"
    "  2026-09-09T21:53 #x — @BK (bankerkyle) you got a new disciple\n\n"
    "roast monsoon and don't hold back"
)
assert _is_message_count_question(question) is False
```
Fix direction: strip the `[VERBATIM RECENT MESSAGES` ... `]` block the
same way the two existing reply-chain markers are stripped (or, more
robustly, only ever score the text *after* the last bracketed
context block, not the whole payload) before running
`_MSG_COUNT_INTENT_RE`.
